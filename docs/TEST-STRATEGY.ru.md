# [(English version) Test Strategy](TEST-STRATEGY.md)

## Цель

Обеспечить работоспособность ключевых бизнес-сценариев CRM йога-студии при
каждом изменении, сохраняя набор тестов быстрым, детерминированным и дешёвым
в прогоне из CI.

Набор представлен как демонстрация моих навыков: 362 Playwright теста,
показывающих многоуровневое покрытие, архитектуру на Page Object Model
и интеграцию с CI, а не просто перечисление эндпоинтов.

## Уровни тестирования

```
                    ┌─────────────────────────────────────────┐
                    │  tests/functional/...                   │  ← UI-сценарии пользователя
                    │  tests/regression/                      │  ← деньги и изоляция
                    ├─────────────────────────────────────────┤
API-покрытие        │  @api tests (direct /api/ calls)        │
Нефункциональные    │  @security @non-functional + performance│
                    └─────────────────────────────────────────┘
                    ┌─────────────────────────────────────────┐
                    │  demo.alenaproyoga.ru (весь набор)      │  ← тест-эндпоинты + заглушки
                    │  tests/demo (self-contained, CI)        │  ← быстрый сигнал на push
                    └─────────────────────────────────────────┘
```

1. **Функциональный UI** — Playwright управляет реальным браузером через
   Page Object Model. Бизнес-домены живут в `tests/functional/<domain>/`.
2. **API** — точечные обращения к бэкенду через те же хелперы
   авторизации/подготовки: быстро, точно, стабильно. Тег `@api`.
3. **Регрессия** — последовательные сценарии вокруг жизненного цикла средств:
   покупка абонемента, списание/возврат баланса, места записи, изоляция
   пользователей.
4. **Нефункциональные** — тесты производительности (загрузка страниц за
   отведённое время), отказоустойчивость / идемпотентность (дубли платежей,
   некорректные вебхуки, повторные отмены), границы безопасности (редиректы
   гостей, ролевая изоляция, CSRF) и базовые проверки доступности.
5. **Основной прогон — demo-поддомен**: весь набор гоняется на
   `demo.alenaproyoga.ru` — это DEMO_MODE-приложение на отдельной засеянной БД
   (`demo_db.sqlite3`, `settings_demo`), где доступны тестовые эндпоинты
   (`/api/auth/test/*`) и заглушки VK / ЮKassa, поэтому ничего не нужно
   скипать.

## Принципы надёжности

- **Детерминированные данные**: тесты создают собственных пользователей/события
  через тест-API хелперы (уникальные телефоны, даты-смещения) и убирают за
  собой (`deleteTestUser`, `deleteCalendarEvent`, идемпотентные предусловия).
  Единственная зависимость — канонический посев (тестовые пользователи s5/s6,
  тарифы, admin/moderator), который гарантирует тест-сервер / DEMO_MODE.
  БД demo отдельная (`demo_db.sqlite3`) и засеивается командой `seed_data`;
  перед прогоном в CI сбрасывается (flush + seed) для полной детерминированности.
- **Изоляция дат**: сценарии календаря используют далёкие будущие даты, у
  каждого сьюта свой смещение дня, чтобы параллельные воркеры не пересекались.
- **Идемпотентный setup**: хелперы (`setBalance`, `purchaseSubscription`, …)
  терпимы к остаткам от прерванных прогонов.
- **Надежные селекторы**: UI управляется атрибутами
  `data-test-id`, что гарантирует отсутствие падений из-за слетевшего селектора.
- **CI**: на каждый push — быстрая проверка сбора (`--list`) и самодостаточный
  `tests/demo`. Полный набор гоняется на demo-стенде по кнопке
  (`workflow_dispatch` — запустить может HR с портфолио) и по ночному
  расписанию, БД перед прогоном сбрасывается тестовым эндпоинтом приложения
  `POST /api/demo/reset-db/` (доступен только в DEMO_MODE: flush + seed).

## Именование и структура

- Папки называют домен/категорию; `test.describe` — группу сценариев; теги
  выбирают категорию: `@functional`, `@api`, `@regression`, `@security`,
  `@non-functional`, `@smoke`.
- Новые тесты переиспользуют `tests/support/pages/*` (POM) и
  `tests/support/fixtures/` (хелперы) вместо дублирования подготовки.
